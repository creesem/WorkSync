SECTION 01

Overview

WorkSync — Command Center + Hybrid AI Prioritization

Coding Agent Handoff | Approved product direction | 2026-10-11

SECTION 02

Mission

Evolve C:\GitProjects\WorkSync into a local-first, Tana-inspired operational workspace. The personalized Command Center is the default landing page. It uses configurable predefined sections (visibility, ordering, global and section filters) and AI-assisted, explainable prioritization backed by deterministic local rules and optional cloud reasoning. Preserve Obsidian Markdown as authoritative human-editable knowledge and use existing WorkSync services wherever possible.

This is an approved product/architecture direction and phased implementation handoff, not evidence that the repository already supports it. Audit the real code before committing to module paths or migrations. Do not treat illustrative examples and proposed interfaces as existing functionality.

SECTION 03

Decisions already made — do not reopen without concrete evidence of incompatibility

  1. Default landing experience: Command Center, with persistent sidebar preferred, contextual details, and global search.
  2. Customization: predefined configurable sections, supporting show/hide, reorder, and filters; not a general-purpose dashboard builder.
  3. Initial sections: Needs Attention; My Priorities; Since Last Check; Meeting Follow-ups; Team Pulse; Review & Automation. Prioritize the first three for the MVP.
  4. Prioritization: AI-assisted recommendations with explanations, evidence, proposed next actions, deterministic constraints, and manual overrides. Separate official P1/P2/P3 priority from suggested attention.
  5. Hybrid model: local deterministic candidate retrieval/ranking always usable; optional cloud reranking/explanation only when configured and policy-authorized. No cloud dependency for the dashboard.
  6. No direct AI write access to authoritative vault records; validate structured recommendations before display. Official task priority, owner, dates, project state do not change merely because AI recommends it.
  7. Overrides: Pin, Focus Today, Defer, Not Relevant, Always Prioritize. Preserve override semantics and record their basis; significant new risk on a deferred item appears as an explicit override conflict, not silent override.
  8. Privacy: permission and data-classification gate before cloud calls; minimum necessary fields; PHI, credentials, and unapproved raw transcripts blocked by default. Redaction alone is not guaranteed deidentification.
  9. Cost: configurable budget with a provisional $10/month experimental ceiling, not a spending forecast; batching, debouncing, cache, accounting, stop at ceiling.
  10. Person identity: runtime-staged candidates, verified bindings auto-resolve, existing Person merges require reviewer approval; preserve Krisp speaker attribution; name-only labels do not prove cross-meeting identity.
  11. WorkSync repository target: C:\GitProjects\WorkSync. Verify current map.md canonical tracker designation, HEAD/branch/worktree, and ongoing Person Identity & Merge implementation before altering work.
  12. Durable journal and startup recovery are in scope where needed; extend existing transaction infrastructure, do not create a competing writer.
SECTION 04

Audit gate — first mandatory work

Inspect map.md, current branch/HEAD and dirty state, architecture/ADRs/specs, GUI/CLI/HTML routes, local HTTP endpoints, WorkSync indexes, Person/Project/Task/Meeting model, Krisp pipeline, review/invalidation system, transactional writer, runtime persistence, tests, and any in-progress worktrees. Deliver a source-cited current-state audit with implemented / partial / extend / net new / unknown / defer for each relevant F01–F18 capability. Identify exact reusable APIs and ownership boundaries. No implementation until audit and integration plan are recorded and reviewed. Do not overwrite user changes or collide with another workstream.

SECTION 05

Intended user journey (MVP)

  1. Launch WorkSync → default Command Center, using saved profile-specific layout or validated defaults.
  2. See three functional sections: Needs Attention, My Priorities, Since Last Check.
  3. Each item shows why it appears, evidence/source, official priority vs suggested attention, freshness, next action, and a canonical record link.
  4. Customize visibility, order, global and per-section filters; changes persist across restart and are reversible via Reset Layout without touching vault data.
  5. Pin/defer/dismiss an AI suggestion without altering authoritative task/project state; view override reason and lifecycle.
  6. If AI/cloud is unavailable, display deterministic results with explicit source-freshness and fallback labeling.
  7. Expand later to Meeting Follow-ups, Team Pulse, and Review & Automation once source contracts are ready.
SECTION 06

Screen and navigation architecture to evaluate

Compare (a) persistent left sidebar + primary content + optional right detail pane (preferred), (b) Tana-like outliner-first, (c) dashboard tiles and drill-down. Decide using existing GUI/HTML architecture, keyboard navigation/accessibility, deep links, multi-window state, and estimated migration cost. Avoid UI rewrites without a demonstrated net benefit. Suggested sidebar destinations: Command Center, My Work, Projects, People, Meetings, Review Center, Automation; expose other types via contextual links/search initially.

SECTION 07

Persistence contracts — conceptual, adjust after audit

Profile layout document, versioned: schema_version, profile_id, default_view, section_order, visibility, global_filters, section_filters, revision, updated_at. Store durable operational preferences separately from records; provide atomic save, migration, validation of known section IDs, unknown-field handling, export/restore, reset. Do not cache authoritative task/meeting copies in layout preferences.

Section result: section_id, query_version, generated_at, effective_filters, items[] (stable entity_id, entity type, status, label, destination, evidence refs, reason, relevant timestamps), total_count, cursor/pagination, source_freshness, availability, error_state. Distinguish legitimate zero results from unavailable/stale source. Keep counts consistent with filters and canonical indexed entities.

Priority recommendation: recommendation_id, entity_ids, model/provider version, policy_version, input_snapshot_hash, suggested_attention, reason_codes, why_now, suggested_next_action, evidence_refs, generated_at, expires_at, validation_status, privacy_mode. No unsupported evidence references. Treat these as derived records; not authoritative task edits.

Override: override_id, profile_id, target_id, kind (pin/focus-today/defer/not-relevant/always-prioritize), parameters, reason, created_at, expires_at/condition, source_revision_basis, status. Explicit user override prevails over AI ranking except that material safety/urgency conflict is visibly surfaced for review.

SECTION 08

AI and prioritization contract

Implement or adapt responsibilities based on repository audit, not necessarily as new classes:

  • Candidate query: deterministic eligibility, ownership, status, evidence, deadlines, blockers and relationships, permissions.
  • Baseline ranker: transparent factors (urgency, impact, dependency, explicit commitments, readiness, recent changes), fixed safety policies, stable fallback.
  • Context preparation: bounded candidate set and source-backed evidence, source revision fingerprints, data-minimization.
  • Privacy gate: classify each payload field and deny restricted categories by default; cloud use opt-in/configured/approved.
  • Provider-neutral reasoner: adapters with structured response schema, timeouts, cancellations, retries, errors, model metadata. No write-service access.
  • Validator: ensure entity IDs/evidence refs exist and are authorized, enforce override precedence, reject hallucinated dates or assignments; distinguish discussed vs committed/explicit Krisp statements.
  • Cache: key by profile, relevant source revisions, filters/candidate set, policy/override revision, privacy mode, provider/model config. Invalidate only material dependencies. Retain minimal sensitive-free diagnostics.
  • Budget meter: actual model token/cost usage when available; request and monthly limits; warning and suspend at cap; local fallback.
  • Evaluation: real but privacy-safe representative workflow examples covering conflicting deadlines, blockers, competing commitments, stale data, speaker ambiguities, duplicate meeting imports, and unsupported AI claims.
SECTION 09

Section behavior

  • Needs Attention: blocked items, overdue/high-impact commitments, material risks, unresolved review exceptions; emphasize impact over mere age.
  • My Priorities: actionable owned tasks/projects, official P1–P3 vs suggested attention; pins and Focus Today.
  • Since Last Check: significant, canonical change events since the last acknowledged checkpoint; acknowledgment is not task completion and duplicate imports do not multiply events.
  • Meeting Follow-ups: source-backed Krisp commitments and unresolved actions, deduped across meetings and tied to verified Person/Project IDs.
  • Team Pulse: assignment distribution, stalled dependencies, handoffs; permission scope and source freshness.
  • Review & Automation: proposed identity merges, ambiguous extractions, failed/retryable jobs, recovery statuses; no PHI in operational logs.

SECTION 11

Single-orchestrator delivery protocol

Assign one orchestrator to own scope, dependency ledger, subagent briefs, acceptance gates, code review and integration. The orchestrator may spawn independent read-only audit sessions first, then focused implementation subagents on isolated branches/worktrees. Subagents cannot mark milestones accepted or merge directly to main. Every task brief states exact baseline/HEAD, allowed file scope, prerequisites, deliverables, tests, and known exclusions. The orchestrator runs integration tests, coordinates with Person Identity & Merge/Krisp branches, maintains next-session handoff and decision log, and resumes from verified commits. If spawning isn't supported, use sequential isolated sessions; don't claim sessions were spawned. Avoid parallel writes to the same files.

SECTION 12

Release acceptance criteria

  • Command Center is the default route; three MVP sections contain real indexed data and correct counts.
  • Sections can be hidden/reordered/filtered and preferences persist safely across restart.
  • Cards navigate to canonical records and return without losing layout/filter state.
  • no matching items is distinct from source unavailable and stale data.
  • Official priorities, owners, dates, and vault entities remain unchanged by AI suggestions or acknowledgment.
  • Evidence-backed AI suggestions have actual authorized citations, model/policy provenance, and clear suggested actions.
  • Name-only Krisp attribution never silently establishes a verified Person binding.
  • User overrides persist and are honored, with a clear conflict state for materially urgent new evidence.
  • Cloud is disabled unless configured/approved; PHI, credentials, and unapproved transcripts do not leave the local system.
  • Model failures, invalid output, offline mode, and budget exhaustion retain a usable local ranking.
  • Cache reuse/invalidation respects changed evidence, policy, filters, overrides and model config.
  • Duplicate meetings/events do not create duplicate feed entries or task effects.
  • Full tests, concurrency/recovery where applicable, accessible controls, log privacy and documented migration/rollback pass.
